# Pro - notes for agents

Why the paid tier's code is the way it is. Read the section of a file before editing it; an edit that changes or cancels a point below updates the point in the same commit.

Codes used below: T1' / T2 / T3 / T4 are the offer's trigger rules and S1-S6 the offer screen's states, both from the paywall spec and handoff; "edge N" is the spec's numbered edge case.

## Pro.swift

- `Entitlement` — the vocabulary of the paid tier is one non-consumable, bought once, kept for good: no subscription, no renewal, no account, so "does this install own Pro" is the whole model. Three states, not two: on a fresh install that has never reached the store, "we have not checked" is a different fact from "not bought", and reading the first as the second tells a paying user their purchase is gone (edge 16).
- `ProCatalog.productID` — must match, character for character, the in-app purchase in App Store Connect (Apple ID 6798140298) and the one in `IFApp.storekit` used for local testing. Not derived from the bundle id: `simple-L.if-app.com` has dashes, and Apple allows only letters, digits, underscores and dots in a product identifier. Permanent — a deleted product does not release its id for reuse.
- `Entitlement.unknown` — not verified yet. Gating behaves as `free` (Pro is never handed out on a guess), but the offer never opens by itself here, and a tap on a lock leads to "purchases not checked yet" with Restore as the first action.
- `Entitlement.isLocked` — `unknown` locks like `free` on purpose.
- `Entitlement.analyticsValue` — the `pro_status` user property: a fixed, unlocalised list. `unknown` is a value of its own, not folded into `free`, or the property would say the app knows something it does not.
- `OfferQualification` — which finished fasts may carry the one-time offer (T1'). A fast abandoned in the first minutes does not qualify, for two reasons pulling the same way: the first paid request in someone's life should not land on their first failure, and such a fast must not spend the single show this install will ever get.
- `OfferQualification.minimumGoalFraction` — a constant, not logic: the final value comes from the distribution of `fast_stopped.duration_hours`, so tuning it is changing this number and nothing else.
- `OfferQualification.qualifies(elapsed:goalHours:)` — reaching the goal needs no branch: a fast at its goal is at 100%, past the fraction. `goalHours` is the goal the fast actually ran to (`AppState.activeGoalHours`), not the plan as it stands now: a plan changed mid-fast must not re-decide whether the fast that just ended earned an offer.
- `PaywallTrigger` — where the offer was opened from. Raw values are the GA4 `trigger` parameter: a fixed ASCII list, never a string that also appears on screen. Named after the action, not the ordinal — the offer routinely appears on a third or fifth fast, so `first_fast` would describe something that did not happen. This is the analytics parameter, not a presentation router.
- `PaywallTrigger.fastFinished` — T1': the first qualified finished fast, after the user left the complete state.
- `PaywallTrigger.planCustom` — T3: the Custom row in the plan editor.
- `PaywallTrigger.streakBreak` — T2: a broken streak, offering the freeze.
- `PaywallTrigger.manual` — T4: a permanent entry the user had to go looking for — the Pro row in the About IF24 sheet.
- `PaywallTrigger.historyExport` — the locked export row in History. Split out of `manual` because it is the one permanent entry whose door names a single benefit: someone tapping a padlock on "History as CSV" has already said which of the three they came for, and the offer leads with it. Folded into `manual`, neither half could be read — the distribution would mix "went looking for the offer" with "asked for the export", and the offer would open on the wrong benefit.
- `PaywallTrigger.home` — the Pro control in the timer header. Kept apart from `manual` on purpose: `manual` means "the user went looking for the offer", this means "the door was on screen and got tapped", and the hypothesis behind a home-screen door is that it becomes the main manual entry. Folded in, the distribution over triggers — the number the release is read by — would be unreadable.
- `PaywallTrigger.unknown` — no entry point on record. Not a door and never dispatched: what reporting falls back to for an event raised while no offer is open (today, restore run from the About sheet's own button). It exists so that "we do not know" is visibly absent from the distribution rather than hidden inside a door — without it `manual` would double as the fallback, and a restore nobody opened an offer for would inflate the very door `home` is compared against.
- `PurchaseFailure` — raw values are the GA4 `reason` parameter, same fixed-list rule as `trigger`.
- `PurchaseFailure.cancelled` — the user backed out of Apple's sheet; not an error state on screen.
- `PurchaseFailure.network` — the one distinction the offer's error state renders differently: two bodies, one visual state.
- `PurchaseFailure.pending` — Ask to Buy: the purchase is waiting for someone else's approval.
- `ProProductInfo.displayPrice` — the store's own formatted price ("$6.99", "¥1,000", "COP 29.900,00"), rendered as one string and never taken apart: currency position, digits and separators are the storefront's business.
- `EntitlementSource` — how the right arrived. It never changes what the user owns or what the confirmation frame looks like, only the words on it: "you just paid", "your purchase came back" and "someone approved it for you" are three different things to happen to you and one thing to own.
- `PurchasePhase` — what the purchase machinery is doing now; about the attempt in progress, not about what the user owns.
- `PurchasePhase.purchasing` — Apple's sheet is up or the transaction is being settled.
- `PurchasePhase.awaitingApproval` — Ask to Buy, waiting for a parent's approval. Not a failure the user caused; resolves later through `Transaction.updates`, with no relaunch.
- `PurchasePhase.granted` — the right is in hand and not yet confirmed to the user. Every way of coming by it lands here: money changing hands is not allowed to be quieter than a free Restore.
- `PurchasePhase.outlivesOffer` — whether the phase describes something still happening off the offer screen and so survives it opening or closing. Ask to Buy is the only one: the request is out with whoever approves it and resolves through `Transaction.updates` whenever they get to it, possibly long after the user walked away. Every other phase is feedback about one presentation and says nothing about the next (edge 18).
- `ProNotice` — the two things the app has to say after the entitlement goes away. They share one sheet and differ only in when it appears: the first at the next neutral moment, the second at the next fast that runs to a different goal. Never shown together: told at once, "Pro is gone" swallows "and your goal is now sixteen hours", and the second is the one that changes what the timer does.
- `ProNotice.entitlementRevoked` — edge 6. The reason is never named: a refund and leaving a Family Sharing group are the same fact to the user, and one key covers both.
- `ProNotice.goalChanged` — edge 17, the other half of edge 9: the fast in flight was allowed to finish on its custom goal, so the next one starting shorter has to be said out loud.
- `OfferState` — the six states of the offer screen as one value. They replace each other in place — no navigation, one grid — so the screen renders this and nothing else.
- `OfferState.offer` — S1, the offer itself.
- `OfferState.purchasing` — S2, a purchase under way.
- `OfferState.failed` — S3. The reason picks the body; both bodies occupy the same pixels, and `cancelled` never lands here (the screen stays on S1).
- `OfferState.awaitingApproval` — S4, waiting for approval (Ask to Buy).
- `OfferState.unverified` — S5, the entitlement has not been checked yet; Restore is the primary action. A pre-check state, not a failure: most people who see it never bought anything.
- `OfferState.granted` — S6, the right is in hand. One frame for all three sources; the source picks the title and the body and nothing else, which is why there is no seventh state for a purchase.

## ProState.swift

- `ProState` — what is owned, what is for sale, and what the purchase machinery is doing. The offer screen's six states are derived here (`offerState`), not stored, so no code path can leave the screen in a state that contradicts the entitlement it is selling.
- `ProState.product` — nil until the store answers, and on every launch that never reaches it.
- `ProState.trigger` — set when the offer opens and carried until it closes, because every purchase event has to say which door the user came in through — the distribution over triggers is the release's one readable result.
- `ProState.revocationPending` — edge 6, waiting for a neutral moment on the timer: not over a running fast, not on the complete state, not over an animation.
- `ProState.goalChangePending` — edge 17, waiting for the next fast to start. Armed at the same instant as `revocationPending` and shown much later, which is the whole point of keeping the two notices apart.
- `ProState.autoOfferShown` — T1' spent. The one-time offer is one time for the life of the install, so this is the one thing about the offer that outlives a launch: loaded at bootstrap, written back on the fact of a show and nothing else. It lives in the app's preferences (`ProOfferRepository`), so a cold start and an App Store update carry it and a delete-and-reinstall clears it. The second half is accepted, not a defect: what keeps the offer from someone who already paid is the entitlement check, not this flag, and a flag that survived deletion would only mean a reinstaller never sees the offer.
- `ProState.autoOfferArmed` — a qualified fast finished and its offer has not been shown. Deliberately **not** persisted: the plan belongs to the session that finished the fast. A session that ends without showing drops it, `autoOfferShown` stays whole, and the next qualified fast arms a new one. Persisted, the offer would greet a cold start with no fast behind it — the ambush T1' exists to prevent.
- `ProState.reviewPromptedThisSession` — the native review request went out this launch, and the offer stands down for the rest of it: both are interruptions, and only one is an asset we keep.
- `ProState.showsNothingToRestore` — restore ran and found nothing. Transient: the service block says so for a couple of seconds and goes back to being a link. Not a seventh offer state — after an empty restore the truth about this user is exactly S1.
- `ProState.isVerifiedFree` — whether this install may be *sold* to: the store answered `free`. Not the same question as `isPro`; the difference is `unknown`. Gating goes through `isPro` and locks on a guess. Selling on a guess is the opposite error and costs more: the person `unknown` describes is often someone who already paid and moved to a new phone, and every selling surface would tell him his purchase is gone (edge 16). Named because two surfaces ask it — `autoOfferPending` and the permanent entry in the timer header; written out at both, the day the rule for `unknown` moves is the day one keeps the old rule and still compiles.
- `ProState.isOfferOpen` — derived from the entry point rather than stored twice: the screen cannot be open without one, nor closed while it still has one.
- `ProState.autoOfferPending` — T1' is owed and nothing on the entitlement side forbids it. Not "show it now": *when* belongs to the screen that renders the eating window (`TimerFlowView.scheduleAutoOffer()`), because the moment is that card being on screen and settled; this side answers only "may it", one definition because both the scheduling and the re-check on arrival ask it. Every condition is a *suppression* and none spends `autoOfferShown` — that is what makes a suppressed show a postponement rather than a loss:
  - `isVerifiedFree` rather than `!isPro`: `unknown` locks like free but must never open the offer by itself; the store may answer seconds later, by which time this moment has passed;
  - `product != nil`: no price, no offer — we do not open a screen that cannot sell;
  - `phase == .idle`: an attempt in flight (an Ask to Buy still out) is not to be interrupted with an invitation to buy the same thing.
- `ProState.offerState` — an attempt in progress outranks everything: while the user waits on a payment, that is the only thing the screen can honestly be about. With nothing in flight, an unverified entitlement shows S5 rather than the offer — we do not invite someone to buy again what they may already own. No product means no price, and the offer is a frame built around one; a configuration error is not the user's unverified entitlement, so it does not belong in S5 (Restore could never resolve it) but in S3, the one state where "something broke" is true.

## ProAction.swift

- `ProAction.offerClosed` — closed by the user, or by the screen itself after a purchase.
- `ProAction.autoOfferArmed` — a fast just ended past the quality threshold and has earned the one-time offer. Arming, not showing: the moment comes later, when the user leaves the complete state through the eating window.
- `ProAction.autoOfferCancelled` — dispatched by whoever invalidates the fast behind the armed show: the rollback that puts the fast back in flight, and the Reset that throws it away. The one-time flag is untouched, so the next qualified fast arms again.
- `ProAction.storeResolved` — what is owned and what is for sale arrive together: they come from the same round trip, and disagreeing halves are worse than a slightly later answer.
- `ProAction.entitlementChanged` — the entitlement changed under us: a purchase made elsewhere, an approved Ask to Buy, a refund, a family member leaving the group.
- `ProAction.purchasePending` — Ask to Buy: the purchase exists but nobody has approved it yet.
- `ProAction.purchaseFailed` — `cancelled` means the user backed out; the screen returns to the offer, not to an error.
- `ProAction.restoreFoundNothing` — not an error: the screen goes back to the offer, now with a verified answer behind it.
- `ProAction.nothingToRestoreExpired` — the transient "nothing to restore" line has had its couple of seconds.
- `ProAction.noticeShown` — a one-time notice reached its moment. Dispatched by whoever owns that moment: the timer flow for edge 6, the start thunk for edge 17.

## ProReducer.swift

- `proReducer` — pure and synchronous. Every transition between the six offer states is here and nowhere else; the screen renders `offerState`, it does not decide it.
- `proReducer` — `.offerOpened` — for `.fastFinished` the one-time flag is spent here and nowhere else: on the fact of a show, the same instant `paywall_shown` is logged. Every suppression on the way leaves it alone, which makes a suppressed show a postponement instead of a loss.
- `proReducer` — `.offerOpened` — a fresh presentation starts clean: an error or confirmation left from the last presentation is not news about this one. A pending approval is not leftover — the request is still out — so the screen opens on S4 rather than inviting a second purchase (`PurchasePhase.outlivesOffer`).
- `proReducer` — `.offerClosed` — same rule: walking away from the offer is not an answer from whoever approves the purchase. The Pro row in About IF24 reads this phase and must keep saying "awaiting approval" until the approval (or a failure) arrives (edge 18).
- `proReducer` — `.autoOfferArmed` — checked against the spent flag here as well as at the show, so an install that has had its offer never arms one again and nothing downstream holds a plan that can never fire.
- `proReducer` — `.entitlementChanged` — losing a right that was verifiably held is the one transition the user must be told about (a refund, a family member leaving the group); both notices are armed here and shown much later, at two different moments. Having Pro again makes both queued notices false, however long ago they were queued. An approved Ask to Buy arrives here: the screen stops saying it is waiting and says the purchase went through (`.granted(.approved)`); the money was taken from someone not necessarily looking at this screen, so the confirmation waits on S6 to be dismissed by hand rather than flashing past. Nothing else about an entitlement change is a statement about an attempt in progress.
- `proReducer` — `.purchaseCompleted` — the one place the app can say "your money arrived" in the second it arrives; it lands in the same S6 the free Restore has.
- `proReducer` — `.purchaseFailed` / `.restoreFailed` — backing out of Apple's sheet is not a failure to report: the offer stays as it was, which is what the user asked for by cancelling.
- `proReducer` — `.restoreFoundNothing` — an answer, not an error: it also settles an entitlement that may have been unknown, so the screen leaves S5. Leaving S5 is its own feedback; the transient line (`showsNothingToRestore`) is only for surfaces where the frame would otherwise not move at all, hence `state.entitlement != .unknown`.
- `proReducer` — `AppLifecycleAction.reviewPrompted` — the review prompt outranks the offer for the rest of the launch. Ratings are a growth asset and cost more than one attempt to sell; the flag stays unspent, so suppressing wrongly (Apple may show nothing — the action means the request was made, not that a panel appeared) costs nothing.
- `proReducer` — trailing guard `isPro && phase == .idle` clears the trigger — the offer does not stand open before someone who already owns it. Stated once, over the state, rather than once per way the right can arrive (bought here, Ask to Buy approved later, the store answering `.pro` for a purchase made elsewhere): different actions, same consequence. The condition is `idle`, not "the screen shows S1", because idle is exactly "nothing in flight": every other phase is feedback on an attempt and has its own frame to finish in (S2 while settling, S4 while approval is out, S6 for the confirmation whatever the source, S3 for a failure worth reading). A purchase goes to `.granted`, not idle, so the screen stands on S6 until dismissed, as a restore does. Analytics is unaffected: the middleware reads the trigger off its pre-reduce snapshot, so `purchase_completed` still carries the door. Standing over the whole switch it also refuses to *open* the offer for an owner — deliberate and today unreachable, because every door is shut from outside (`ProRowStatus.opensOffer` in About, the export button's `isPro` check, `TimerFlowView.confirmPlan(hours:)`'s plan check, `TimerFlowView.showsProEntry(state:)`, `ProState.autoOfferPending`). A new door added without its own guard would still be wrong: the analytics middleware logs `paywall_shown` on the action and would report a screen that never appeared. The guard belongs on the door, not here.

## ProNoticeSheet.swift

- `ProNoticeSheet` — one sheet, two things to say after the entitlement goes away: that it is gone (edge 6) and that the next fast runs to a different goal (edge 17). They share a component and never a frame — the second arrives at the next start, possibly days later. A sheet, not an alert, toast or banner: an alert's convention is "we need a decision from you", there is none, so it reads as an error, and it is 238pt wide, which gives Korean three lines at larger type sizes; a toast or banner can swallow the second sentence, which is the entire reason for showing this. No Restore button: after a refund it would return nothing.
- `ProNoticeSheet.sheet(_:bottomInset:)` — the title is 17/semibold and deliberately not the 25/600 state-headline slot, which overflows in English, Ukrainian, German and Polish at xxLarge. Accessibility ids `proNotice`, `proNotice.close`.
- `ProNoticeSheet.body(_:)` — `.entitlementRevoked` — the cause is never named and no locale mentions money: one key covers both a refund and leaving a Family Sharing group.

## PaywallView.swift

- `PaywallView` — six states on one grid: they replace each other in place, which is why nothing here navigates and why the price block sits at the bottom of a flexible column rather than at a measured offset. Positions come from what the text actually took, never pinned to the English measurement — the S4 body is 56pt in English and 76.5pt in Korean at the same type size. Every vertical slot is a `minHeight`: a `frame(height:)` on any slot that carries text clips Japanese and Korean at the default type size. The floors are English measurements, so on a column with no room to spare they step aside (`Metrics`).
- `PaywallView.trigger` — which door the user came through: it decides which benefit leads, and the framing line belongs to that benefit.
- `PaywallView.body` — content only; the opaque surface is `PaywallBackdrop`, drawn by the flow outside the part that switches. Three candidates of the same column in a `ViewThatFits`, first that fits wins. The offer was drawn at 390 × 844 (`IF24 Pro Offer.dc.html`); a 375 × 667 screen is 177pt shorter, and in text-heavier locales the third benefit ended up under the bottom fade at default size (en, de, ja, uk, fr) — in Japanese the fade reached the row's title too, and a dimmed dot over a dimmed title reads as a disabled benefit rather than a cut one. `.roomy` is the handoff's default frame unchanged, so every screen that fits it gets exactly the verified layout. `.tight` is the handoff's own answer to a column out of room — the overflow frame (group E, "S1 · xxLarge") tightens the same three gaps and nothing else. The scrolling candidate is the floor under both: at xxLarge — the Dynamic Type ceiling `AppFlowView.body` pins — no set of gaps fits the longer locales, and the fade over a scrolling region is what that frame draws.
- `PaywallView.Metrics` — the vertical numbers of the column, the only thing separating a screen with room from one without. The slot floors are English measurements — `spec.md` gives "Title slot height 40" and "Body slot min-height 56", and says its pt values "come from Hanken metrics and do not transfer" to ar/ja/ko/zh/uk. They hold the grid steady across the six states while there is room; without room, a one-line Japanese framing line reserving two English lines of empty space is 25pt taken from the benefit list below.
- `PaywallView.Metrics.priceGap` — reading matter to the price block, a gap that cannot collapse, so a clipped last benefit never touches the price.
- `PaywallView.Metrics.roomy` — group A, "S1": close margin-bottom 10, list margin-top 26, price block `margin-top: auto` (26 is this app's floor under that elastic gap).
- `PaywallView.Metrics.tight` — group E, "S1 · xxLarge": close margin-bottom 6, list margin-top 20, price block padding-top 12.
- `PaywallView.column(_:scrolls:)` — Close above, price and button below, reading matter between. The two controls are never what goes off-screen: at xxLarge in German the title takes two lines and the S4 body four, and one scroll view over the whole column would carry Close off the top and Buy off the bottom at once; both must be reachable in one gesture at any size. In the non-scrolling column the `Spacer(minLength: priceGap)` makes the gap a floor, so the slack above the price block belongs to the reading matter, not to a fixed offset.
- `PaywallView.scrollingReading(_:)` — for the accessibility type sizes, where no set of gaps fits. Scrolls, and its bottom edge dissolves over `fadeHeight` instead of being cut. `contentMargins(.bottom, fadeHeight)` lets the last line travel out from under the fade — otherwise scrolling to the end leaves the very words the fade promises half-transparent; it only adds scrollable slack. A mask rather than the handoff's opaque `--bg` overlay: the surface carries the phase tint (`PaywallBackdrop`), and a flat rectangle of the base colour would print a pale block over it; fading the content's own alpha is the same picture on any backdrop.
- `PaywallView.fadeHeight` — 36pt, from the overflow frame in `IF24 Pro Offer.dc.html` (not in `spec.md`).
- `PaywallView.closeRow` — while a charge is pending the control stays where it is and stops responding; removing it would move the layout under a thumb already travelling. The 44pt target overhangs the gutter by 10 so the glyph, not its target, lines up with the content edge. Accessibility id `paywall.close`.
- `PaywallView.marker(_:)` — a phase dot, or once the purchase is in a green check in a box of the same width, so the list does not reflow when the state changes.
- `PaywallView.bottomBlock` — the wedge (`strings.Pro.wedge`) is the product's whole argument and the mockup has no slot for it in any of the six frames — an omission, not a decision — so it goes where the copy says: under the badge, above the button, at body size. Accessibility id `paywall.price`.
- `PaywallView.primaryAction` — `.awaitingApproval` — flat on the track colour with no green shadow: dimmed green reads as "tap harder", and there is nothing to tap harder at. Accessibility ids `paywall.buy`, `paywall.restore`, `paywall.done`.
- `PaywallView.secondaryBuy` — S5 only: Restore takes the primary slot, so Buy drops to the outline variant.
- `PaywallView.serviceBlock` — Restore and Privacy as two views with a divider view between them, never one string with a separator inside, which in Arabic sends the neutral character somewhere the reader does not expect. Accessibility id `paywall.restoreLink`.
- `PaywallView.serviceBlock` — `showsNothingToRestore` — the line takes the whole 327pt (375 minus the two 24pt gutters) and the divider and Privacy stand down for its two and a half seconds — the same move S5 makes. Sharing the row would stack it at xxLarge in Ukrainian and German, growing the block by 1.84pt and shrinking it back: a layout animation, which the motion spec forbids. Wrapping is not an option either — Japanese breaks onto its last character, which no line-breaking rule protects.
- `PaywallView.isGranted` — S6 whichever of the three ways the right arrived: the badge, the check marks in place of the phase dots and the Done button do not know what paid for them.
- `PaywallView.showsRestoreLink` — the offer keeps its own Restore link everywhere except the two states where Restore already owns a button.
- `PaywallView.title` — `.granted` — one frame, three headlines: this is the whole of what the source changes on screen, so the source is stated, not inferred.
- `PaywallView.bodyText` — `.failed` — the network case names the network, because "something went wrong" sends a person to look for a fault that is neither theirs nor ours.
- `PaywallView.bodyText` — `.granted` — a restore moved no money and says nothing about it. The two paid sources name the sum, and fall back to naming where to find it rather than to an empty line or a live `%@`.
- `PaywallView.framingLine` — the framing line introduces the lead benefit, so it moves with it: one line per lead, decided by the same `trigger` switch that orders `benefits`. Two independent expressions would let the sentence introduce a benefit the list no longer starts with — a padlock on "History as CSV" opening an offer whose first sentence is about plan length.
- `PaywallView.benefits` — from a broken streak the protected day leads: it is the thing that just failed. From the locked export the export leads, for the stronger version of the same reason — the person asked for it by name. Everywhere else the person has never seen a streak badge, and a freeze would be insurance against an event they do not know exists.
- `PaywallView.wedgeColor` — the wedge dims with the price block rather than on its own ladder. Left at `--secondary` it became the darkest thing on screen exactly where the price above it stands back, and the wedge is an argument for the price, so it cannot outrank it.
- `PaywallBackdrop` — the offer's opaque surface: the theme's base colour with the phase glow, tinted by the phase the user came from so the offer stays attached to the screen that called it. A type of its own, drawn by the flow *outside* the part that switches: the six states replace each other by identity and cross-fade, and mid-fade both layers stand at partial alpha, so a background inside the switched layer stops being one for the length of the transition (the timer read through the offer on the way into Confirming and again after the charge went through). Anything opaque belongs on this side of the `.id`.
- `PaywallBackdrop.body` — the handoff's tint is `radial-gradient(130% 55% at 50% 0%, phase 16%, transparent 72%)`. Those two numbers are *radii* — 1.3 screen widths across and 0.55 heights down from a centre on the top edge — so the ellipse's box is twice each, and the strong end of the gradient lands on the top edge of the screen. Using the radii as the box puts the core a quarter screen above the screen and leaves only the faded tail visible (5-7% instead of 16%). Drawn as a circular ramp squashed into the ellipse rather than with `EllipticalGradient`: the CSS ramp is linear in alpha and ends at a stated fraction of the radius, while `endRadiusFraction` is a fraction of a size SwiftUI does not name (measured against the handoff it ran a third of a screen long); `startRadius`/`endRadius` are points, so the 72% stop is the CSS number rather than a fitted value. The far stop keeps the phase's hue and drops only alpha: fading to `.clear` fades towards transparent *black* and prints a grey haze halfway down the light theme.
- `OfferButton` — its own type rather than `PrimaryButton`: 54pt on a 16pt radius with a 600 label, a disabled shape flat on the track colour, and an optional spinner — none of which the footer's button needs. The shadow is `--shadow-cta`, not the footer button's glow: in the dark theme the handoff drops the green halo for plain black, so the button sits on the surface instead of lighting it.
- `Spinner` — a quarter arc turning at a constant rate over a faint full ring. Pinned left-to-right: a spinner that reverses in Arabic reads as undoing rather than working.

## PurchaseProThunk.swift

- `PurchaseProThunk` — the Buy button end to end: mark the attempt, run Apple's sheet, report how it ended. The four endings are separate actions, not one with a flag, because they lead to four different offer states (S6, S4, back to S1, S3). Guards on `isPro`, which is what makes a tap on an owner's open offer do nothing.

## RefreshEntitlementThunk.swift

- `RefreshEntitlementThunk` — asks what this install owns and what the product costs in one thunk: it is one round trip, and the answer to "is it owned" depends on whether the store could be reached at all, which is what the product lookup establishes.

## RestorePurchasesThunk.swift

- `RestorePurchasesThunk` — the only way back to Pro on a new device (there is no account, by design) and the first action offered when the entitlement has not been verified.
- `RestorePurchasesThunk.execute(state:dispatch:)` — `.nothingToRestore` — the transient line retires itself. The wait lives here, not in the view, because a view that schedules its own delayed work owns a timer whose lifetime is the frame's, not the answer's.
- `RestorePurchasesThunk.transientNanoseconds` — 2.5s: long enough to be read once, short enough to be gone before the next tap.
