# Flows - notes for agents

Why the flow views (the store-connected screens) are the way they are. Read the section of a file before editing it; an edit that changes or cancels a point below updates the point in the same commit.

## AppFlowView.swift

- `AppFlowView` — the root flow: owns the store, presents the current screen and hosts the offer.
- `AppFlowView.body` — `NavigationStack` exists for the one push in the app, the history screen.
- `AppFlowView.body` — offer overlay — a full surface rather than a `fullScreenCover` because its appearance is specified in numbers (28pt of travel over 420ms, no overshoot) and the system cover brings its own. Hosted here, not on the timer, because one of its doors — the export lock — is on History, a screen pushed onto the timer: an overlay on the timer renders under that push, so the offer would open behind the screen it was called from, compile cleanly and keep the timer's doors' tests green. The common ancestor of all entry points is the only place where the z-order is right by construction; it also keeps History alive underneath with its scroll position, which is what closing the offer returns to.
- `AppFlowView.body` — `.dynamicTypeSize(...DynamicTypeSize.xxLarge)` — the timer's centre is a fixed 232pt circle holding a fixed 176×40 caption slot and the footer buttons are fixed-width, while `Font.custom` scales with the system text size, so past a point text outgrows containers that do not move ("Закривається о 20:00" clips to "Закриваєтьс…" in the circle). Capping once, at the root, keeps every screen within the sizes the layout was drawn for. The proper fix is a layout that stretches (`ScaledMetric` on the slots); this ceiling holds the line until then. Presented sheets (About) start their own environment and the ceiling does not reach them — deliberately: four locales overflow About's Pro row at xxLarge already, and its slots are built to stretch.
- `AppFlowView.offerTint` — the tint the offer wears, taken once, on the opening edge in `onPropsChange`, and held while the offer is up.
- `AppFlowView.offerPhaseColor()` — reads the one definition, `TimerScreenProps.offerPhaseColor()`. A view-side derivation and deliberately not an argument of `offerOpened`, which would put a clock reading into an action. Frozen at opening on purpose: it describes the phase of the screen the offer was called from, that screen is fully covered while the offer is up, so a later tint has nothing on display to agree with. It cannot honestly be a field of `AppProps` either — the phase advances with the clock, not the state, so a mapped prop would go stale between actions and then jump on an unrelated one. In `@State` it changes at one named moment.

## AboutFlowView.swift

- `AboutFlowView` — the About IF24 sheet wired to the store. Beyond presentation its only job is mapping a three-valued entitlement plus an attempt in progress to the four statuses the Pro row can say, and the rule that an unverified entitlement opens the offer at S5 (`OfferState.unverified`) rather than at the offer itself.
- `AboutProps.init(state:)` — `.unknown` maps to `.notCheckedYet`, never "inactive": we have not looked, and a lock is caution while a status is a claim.
- `AboutFlowView.onSunnah` — the Sunnah door is handed up rather than presented here. The reminders screen has two entries (the plan editor's row and this one), and a screen with more than one entry is presented from the nearest common ancestor of its entries (the decision on screens with several entries in `ARCHITECTURE.md`) — the timer, which already hosts this sheet and the plan editor. Presented here it would get a second host and a second flag, and the two doors would disagree about where closing the reminders screen lands.
- `AboutFlowView.body` — `onOpenOffer` — the permanent entry reports `.manual` whichever state the offer opens in: the value names the door, not the frame behind it.
- `AboutFlowView.body` — `onOpenSource` — `sourceOriginalOpened` is dispatched here, not from `OpenExternalLinkThunk`: the same thunk opens the privacy policy and the system Settings, and an event inside it would report those as papers.

## PaywallFlowView.swift

- `PaywallFlowView` — the offer screen wired to the store. It owns nothing about how the offer looks (`PaywallView`), only which of the six states is true now and what the four actions dispatch. Motion is from the handoff and stated in numbers: the screen rises 28pt over 420ms with no overshoot, and the six states cross-fade in 180ms without animating layout. A cross-fade cannot move the Buy button under a thumb already travelling; a layout animation can.
- `PaywallProps.isOpen` — not rendered: it decides whether the rest of the props are still worth applying (see `onPropsChange` in `body`).
- `PaywallProps.init(state:)` — `trigger ?? .unknown` — only the closed-offer snapshot reaches the nil branch, and `onPropsChange` drops those, so it decides nothing anyone sees; `.unknown` orders the benefits exactly as `.manual` would. Spelled `.unknown` because it is not a door: a value naming a door the user did not come through, even off-screen, is how the two meanings got mixed.
- `PaywallFlowView.phaseColor` — passed in, not derived here: it is the phase at the moment the offer was called, not necessarily the phase by the time the user finishes reading.
- `PaywallFlowView.body` — scrim — warm, under the screen, so whatever called the offer does not read through while the card is still travelling.
- `PaywallFlowView.body` — `PaywallBackdrop` stays outside the view that carries `.id(props.state)`: a cross-fade stands both layers at partial alpha mid-way, and a background that fades with them is not a background.
- `PaywallFlowView.body` — both `zIndex`es are load-bearing. Mid-swap the stack holds three children (surface, outgoing state, incoming state); without an explicit order SwiftUI put the outgoing one *under* the surface, it vanished on the first frame instead of fading, and the card went blank for ~80ms mid-transition.
- `PaywallFlowView.body` — surface and contents rise together: the 28pt of travel is the card's, not the text's.
- `PaywallFlowView.body` — `onPropsChange` — a screen on its way out keeps the state it was in. `offerClosed` clears the entry point and resets the purchase phase in one action, so the last props would cross-fade the frame on screen (the S6 confirmation, say) back into the plain offer with Buy — and reorder the benefits as the trigger goes nil — under a removal already running. Nothing said after the offer closes has a reader.

## TimerFlowView.swift

- `TimerFlowView` — the fasting screen on Redux: reads a `TimerScreenProps` projection and derives phase and fraction from elapsed against the cycle's goal. Elapsed is never stored; it comes from `fastStartTimestamp` and a `TimelineView` tick.
- `FooterHeightKey` — carries the pinned footer's measured height up to the scroll content that reserves it. A preference rather than a second `GeometryReader` because the two live in different branches of the same `safeAreaInset` composition.
- `TimerScreenProps.eatingEndTimestamp` — projected from the timer state, not recomputed here, so the screen and the window-closed push agree on the moment.
- `TimerScreenProps.plan` / `.goalHours` — not the same fact. `plan` is what is selected (the header pill, the editor); `goalHours` is the goal of the cycle on screen. A plan changed mid-fast, or a custom goal whose entitlement went away, leaves the fast in flight running to the goal it started with.
- `TimerScreenProps.minutesAgo` — the picker's value as the user expressed it, a distance; it becomes a clock time only for display, where it is displayed.
- `TimerScreenProps.hasRecords` — the header pill only exists once there is a record to open.
- `TimerScreenProps.lastFastDuration` — length of the newest finished fast: the eating window's link into history.
- `TimerScreenProps.endFast` — the end-of-fast sheet is a whole value, not a flag: which of its four cards is up, and every label on them, is decided from it.
- `TimerScreenProps.isPro` — drives the lock on the custom plan row and whether the offer is up.
- `TimerScreenProps.isVerifiedFree` — whether the header's Pro entry has anyone to sell to. `!isPro` cannot answer it: `unknown` locks like free but must not be sold to, and negating `isPro` folds it in on the wrong side. The definition lives on `ProState`, shared with the automatic offer, so the two surfaces cannot drift on what `unknown` means.
- `TimerScreenProps.notice` — the one-time notice on screen, or the one still waiting for a neutral moment.
- `TimerScreenProps.autoOfferPending` — the post-fast offer (T1') is owed and the entitlement side has nothing against it. Whether this screen is the place to show it, and when, is decided by `TimerFlowView.scheduleAutoOffer()`.
- `TimerScreenProps.screenState(progress:now:)` — an open eating window shows the countdown until it closes; once closed, the chain screen (count-up + Continue fasting) holds for `TimerState.closedWindowHorizon` (24h), then falls to idle. Running past the goal is `.goalReached` (overtime), otherwise `.active`.
- `TimerScreenProps.offerPhaseColor()` — the offer inherits the phase tint of the screen it was called from; an open or closed eating window has no phase on screen, so the offer takes the neutral green its backdrop already uses. Lives on the props rather than on a view because two hosts need it — the timer, which the tint describes, and `AppFlowView`, which presents the offer. A second copy in the root would compile and then drift (invariant 8).
- `TimerFlowView.sunnahRequestedFromAbout` — a note between two updates, not state: the About sheet's Sunnah row was tapped and the sheet is on its way out. The reminders screen opens on the far side of the dismissal and the flag is spent there (`openSunnahIfRequested()`).
- `TimerFlowView.historyFocus` — the record History opens on: the fast a refusal named, so the person sent there to delete it does not have to hunt for it.
- `TimerFlowView.historySource` — which entry point opened the history: it names the analytics source, and the eating-window entry also decides that the record just closed opens with it.
- `TimerFlowView.goalSealScale` / `.goalHaloOpacity` / `.goalSweepAngle` / `.goalSweepOpacity` — the goal moment and overtime glow are driven here so the one-shot plays only on a genuine live crossing and is not replayed when relaunching mid-overtime.
- `TimerFlowView.goalMomentPlayed` — whether the goal moment has already played for the `.goalReached` frame on screen. Needed because the moment has two entries — the state edge and the view appearing already in `.goalReached` — and one crossing can arrive through both. The reducer is idempotent; the haptic and the `goal_reached` event are not. Cleared by the first sync that sees any other state: leaving the frame makes the next entry a new moment.
- `TimerFlowView.footerHeight` — measured, not assumed: the footer moves with the state, the locale and the text size, and the scrolling middle reserves exactly this much at its bottom so its tail can be scrolled clear of the card.
- `TimerFlowView.body` — `TimelineView` — ticks every second only while a fast runs or an eating window counts down.
- `TimerFlowView.body` — overlay animations — the sheets ship transitions, but props land from the store as a plain assignment; without an animation bound to each flag the transition never runs and the sheet pops in. Scoped per flag so the per-second ticks stay unanimated.
- `TimerFlowView.body` — the offer is not presented here: it lives in `AppFlowView`, because History is pushed on this screen and an overlay hosted here would render under it (the history's export lock is a door into the offer).
- `TimerFlowView.body` — About sheet `onDismiss` — the reminders screen's second door lives inside the About sheet, and one sheet cannot be swapped for another in a single update: SwiftUI drops the second presentation and nothing appears. So the row only asks (dismisses About, leaves a note) and the note is spent in `openSunnahIfRequested()` once the dismissal has finished. The reminders screen stays presented from this one host — the `ARCHITECTURE.md` rule for a screen with several entries — and both doors land back on the timer on close.
- `TimerFlowView.body` — `onChange(of: props.offerOpen)` — About is a door into the offer and the offer sits behind it, so opening the offer closes About (and Sunnah). The pending Sunnah request is dropped too: the person asked for the offer, not for reminders rising behind it.
- `TimerFlowView.body` — `onChange(of: noticeMoment)` — the revocation notice (edge 6) waits for the nearest neutral moment: not over a running fast, not on the complete state, not over the goal animation. Nothing is lost by waiting — the lock is already back, this is only the sentence about it.
- `TimerFlowView.body` — `onChange(of: props.isEating)` — the eating window opening is T1''s cue, and the edge is caught out here rather than inside `screen()`: opening the window flips the `Group` from the untimed branch to the `TimelineView` one, so that subtree (and any `onChange` in it) is rebuilt rather than updated. Out here the view is stable and the edge arrives.
- `TimerFlowView.body` — History is a push, not a sheet: it is deeper into the app, not a dialog over it.
- `TimerFlowView.body` — `onAppear` — restores the settled overtime end-state on a relaunch mid-overtime (`onChange` does not fire for the initial state); reconciles an eating window that elapsed while the app was closed; and presents a revocation that landed while the app was shut, since `onChange(of: noticeMoment)` would never fire for it.
- `TimerFlowView.body` — `onChange(of: scenePhase)` — the goal can be crossed in the background; the moment waits until the user is looking. Every foreground counts as an "open" for the review fallback; the cold start is covered by `onAppear`, because the initial `scenePhase` may already be `.active` and this `onChange` alone can miss it.
- `TimerFlowView.backgroundLayer(theme:)` — `.eating` and `.eatingOver` get the neutral window backdrop: an open window's elapsed is zero and would tint the screen amber (Fed) as if a meal had just landed, and after the window closes but before the next fast there is no phase scale on screen and no elapsed to derive a phase from.
- `TimerFlowView.screen(theme:now:)` — layout — the header is a transparent floating overlay above a full-height `ScrollView`, just below the status bar with no backdrop, so the ring scrolls *under* the plan pill and icons and stays visible around them. The footer is pinned above the home indicator; the middle (ring, editorial, timeline) scrolls between them so a short screen (SE) can reach the timeline while the full 280pt ring keeps its resting spot. The content reserves `headerTop + headerHeight + headerGap` at its top (header controls are ~34pt tall).
- `TimerFlowView.screen(theme:now:)` — `.eatingOver` — the count-up is already the next fast in waiting; the Last-meal control (seeded to the close moment) sets where "Continue fasting" backdates to.
- `TimerFlowView.screen(theme:now:)` — `PhaseRing` — a gap is reserved only while the goal seal sits on the arc. Whether the ring closes is asked of `PhaseProgress.isComplete` — the one definition of a goal taken — not of the screen state: a fast ended at five minutes also lands on `.complete` and must not close the ring around a check it did not earn. A fast that is over has no moving leading edge, so no head dot on `.complete`.
- `TimerFlowView.screen(theme:now:)` — `HistoryLink` on `.complete` — lives in the scroll content, not the footer: in the pinned zone it would stand last in the stack, the strongest position after the primary, so a zero-consequence navigation would outrank the only reversible control on the card and cost footer height it cannot spare. Here the footer edge separates it from the actions; it keeps its label, chevron and 44pt target, and takes `mut` because it is a signpost, not a choice. Accessibility id `timer.savedToHistory`.
- `TimerFlowView.screen(theme:now:)` — bottom padding `12 + footerHeight` — the card is drawn over the content, not beside it. Without the reservation the middle ends where the screen does, its tail sits under the card and the scroll has nowhere to travel, so the row there is not merely covered but unreachable — while its accessibility bounds keep reporting a rectangle no longer on screen.
- `TimerFlowView.screen(theme:now:)` — `onPro` — the offer is presented from the root and its state is derived from `ProState`, so another door into it is one dispatch and nothing else.
- `TimerFlowView.screen(theme:now:)` — footer `safeAreaInset` — lifts off the bottom by the home-indicator inset, or a 32pt minimum on home-button devices (inset 0). The opaque `backgroundBase` backdrop stops the translucent card from showing the scrolling middle through; the phase gradient has fully resolved to `backgroundBase` by the footer, so the seam is invisible.
- `TimerFlowView.screen(theme:now:)` — `.ignoresSafeArea(.container, edges: .bottom)` must stay: it lets the ring keep its full 280pt and run *behind* the card instead of being cut at the card's top edge — the composition the owner chose over a compact ring. It also cancels the reservation `safeAreaInset` would make (that inset contributes to the container region), so the reservation is made by hand from the measured height. The two are not interchangeable: the inset's own reservation shortens the scroll viewport and clips the ring at the boundary; a bottom padding on the content does not.
- `TimerFlowView.screen(theme:now:)` — `onChange(of: state)` — the goal crossing is time-driven, so it is caught inside the per-second tick; the outer body would not re-evaluate to see it.
- `TimerFlowView.screen(theme:now:)` — `onAppear` — an edge is not the only way into a state. `body` switches branches on `isRunning`/`isEating`, rebuilding this subtree wholesale; confirming a back-dated last meal past the goal starts the fast and flips the branch in one step, so the screen is *born* in `.goalReached` and an `onChange` on a just-created view never sees its first value. The outer `onAppear` cannot stand in: it ran once, on the idle screen, before the flip. `goalMomentPlayed` keeps the two entries from playing one crossing twice.
- `TimerFlowView.footer(state:elapsed:theme:)` — `.complete` `onSkip` — no confirm sheet, unlike `.goalReached`: nothing irreversible is left to protect; the fast is already in the history and Resume is the way back.
- `TimerFlowView.footer(state:elapsed:theme:)` — `.eating` `onSkip` — asks first; `.eatingEnded` is dispatched from `EndEatingConfirmSheet`.
- `TimerFlowView.footer(state:elapsed:theme:)` — `.eatingOver` `onSkip` — `MealAction.cleared` drops the seeded window-close time so idle starts fresh.
- `TimerFlowView.consequenceLine(elapsed:)` — exactly one sentence, never none and never two, chosen by whether the day was counted, not by how close the fast came. Muting the line after the near-goal guard was rejected: the sentence *is* the loss the guard warned about, and muting it leaves the fast that fell short as the one where nothing says the day was not counted. The 15-minute near-goal threshold belongs to the sheet — it warns *before* an irreversible tap; this line speaks *after*, and a fast eight hours short is no less uncounted than one eight minutes short. The condition is asked of `PhaseProgress` (where "goal reached" is defined) rather than spelled `elapsed >= goal`: another copy of that predicate is how the footer and the history row disagreed about one fast. Derived, not stored, for the same reason.
- `TimerFlowView.screenIsClear` — nothing is presented over the timer (no sheet, pushed screen, offer or notice). One definition because both one-time surfaces — the revocation notice and the automatic offer — need it, and neither may land under the other or under a sheet; both are spent the moment they are shown, so a show nobody sees is a show lost. The About sheet is the likeliest cover: it is where a refund is noticed.
- `TimerFlowView.noticeMoment` — neutral means nothing in flight: no fast running, no completed fast waiting to be acknowledged, no eating window counting down, nothing presented over the screen.
- `TimerFlowView.showsProEntry(state:)` — two conditions answering different questions. `isVerifiedFree` is about the person: only a verified free entitlement is sold to, and after purchase the control disappears for good — the one reward the app can hand over silently is that it stops selling. The screen state is about the moment: the goal frame and the result screen are where the fast is shown as taken, and nothing is sold there (the rule T1' already follows); a permanent control there would walk around it by construction.
- `TimerFlowView.openSources()` — the About sheet is the app's own document and a door into the offer. `sourcesOpened` is dispatched here, the single opening point, not from the sheet: a redraw is not an opening.
- `TimerFlowView.openSunnahIfRequested()` — `sunnahOpened(source: .about)` goes out here, after the dismissal, not on the tap. The request can be dropped on the way down (the offer rising over the sheet cancels it), and logging at the tap would count an opening the user never saw. The plan editor's door is an overlay that opens in the same update as its tap, so there tap and opening are one moment; here they are two, and this is the one that means "the screen opened".
- `TimerFlowView.autoOfferDelay` — 420ms from the eating window card arriving to the offer starting to rise, from `design-handoff/paywall/brief.md`. The card has no animated transition, so the state change is the moment it is settled; the rule the number serves is "never over a transition". Equal to the offer's rise duration in `PaywallFlowView` by coincidence: the handoff names them as two numbers and either may be retuned alone — do not fold them into one constant.
- `TimerFlowView.scheduleAutoOffer()` — T1', the one-time offer earned by the fast that just ended: shown once the user has left `.complete` through the eating window and its card is on screen, never on `.complete` itself, where a modal would shift the anchor of the window they are about to open. The goal animation cannot be underneath by construction — it belongs to `.goalReached`, two user actions back. Everything is re-checked on arrival: during the delay the window can be skipped, a sheet opened, the store answer late, the app backgrounded, and each is a suppression that must not cost the show. Not dispatching is the whole mechanism — the flag is spent by `offerOpened` and nothing else.
- `TimerFlowView.confirmPlan(hours:)` — a custom length without Pro is where the lock bites: the picker turns freely up to here, and this is the only point at which its value is written to the store. The editor deliberately stays open behind the offer, so someone who came to change their plan is not sent back to start over, and the draft survives.
- `TimerFlowView.overlays(theme:)` — `LastMealPickerSheet` — reading the clock to *show* a value is what the flow is for; what travels in the action is the distance, with no clock in it.
- `TimerFlowView.overlays(theme:)` — `onScrub` — a plain action, not a thunk: dragging emits a value every snap step (up to ~20 a second) and each must land in the order the finger produced it, while a thunk dispatch hops onto an unstructured `Task` with no ordering promise. Affordable only because the payload is a bare distance — no clock to inject, nothing a thunk would be for.
- `TimerFlowView.overlays(theme:)` — meal picker `onClose` — dismissing is a cancel, not a quiet confirm (acceptance criterion "Dismiss = cancel"). Without `MealAction.pickerDismissed` the sheet's edits stay applied: picking "Last night" then tapping the scrim left the pill promising a fast back-dated a full day, and the next primary tap started one.
- `TimerFlowView.overlays(theme:)` — `onKeepFast` — the safe action is the named form of closing the sheet, so it does exactly what the scrim does: no record, no streak change, the fast carries on from the same start.
- `TimerFlowView.overlays(theme:)` — `StreakMilestoneSheet` `onDismiss` — `ReviewMiddleware` listens for `streakMilestoneClosed`; the native review request may follow once the milestone moment is fully over.
- `TimerFlowView.editorial(state:progress:elapsed:)` — takes `elapsed` and not only `progress` because `PhaseProgress.fraction` is clamped at 1 and past the goal no longer carries how far past.
- `TimerFlowView.editorial(state:progress:elapsed:)` — `.goalReached` — encouragement has a ceiling, the same one the end-of-fast sheet uses (`EndFastState.overtimeNeutralThreshold`, 24h): past a day of overtime the app assumes the timer was left running. Without it the main screen would cheer a fast that the sheet under the same button is offering to correct — one app saying two things about one fast.
- `TimerFlowView.reconcileEating(_:)` — keeps the persisted eating flag and the Last-meal control in step with the derived state. An elapsed window holds `isEating` through `.eatingOver` (the chain screen is computed from the same timestamps); only the horizon timeout drops to idle, clearing the flag and the seeded meal time. Entering `.eatingOver` seeds the Last-meal control to the close moment, so "Continue fasting" backdates from there by default. An end-eating confirm left open when the window closes on its own is closed: the question is about an open window, and confirming would end one already ended.
- `TimerFlowView.overtimeShort(_:)` — the footer's OVER value: `M:SS` under an hour, `H:MM` past one.
- `TimerFlowView.syncGoalMoment(to:)` — plays the one-shot moment (+ haptic + analytics) only on a genuine first crossing; a relaunch mid-overtime (`hasCelebrated` set) restores the settled end-state and dispatches `goalScreenSettled` at once. Requires `scenePhase == .active`: iOS renders backgrounded apps for app-switcher snapshots, and a plain state check would burn the moment with nobody watching; the `scenePhase` handler replays it once visible. Played once per entry however many callers report it (state edge, appearing in `.goalReached`, returning to foreground). The day key is stamped by `CelebrateGoalThunk` from the fast's own start + goal, so a fast crossing midnight credits the day the goal was reached — the same day history credits. `goalScreenSettled` is held 1.6s so the seal and sweep finish before anything (the review sheet) can cover them, and re-checks the state on arrival in case the fast was ended meanwhile.
- `TimerFlowView.openMealPicker()` — opening the picker is two facts: the sheet is up, and this is the answer to restore if it is dismissed. One place because both entries (idle and window-closed) must take the restore point; an entry that forgets it brings the "dismiss applies the edit" bug back.
- `TimerFlowView.clockTime(_:)` — `Locale.latinDigits` keeps the region's 12/24h convention (and the device's 24-Hour Time setting) while forcing Latin digits, so the footer clock matches the hand-built timer and chip numerals instead of Eastern Arabic digits in ar.

## HistoryFlowView.swift

- `HistoryFlowView` — what the fasts add up to, then the fasts grouped by month. Pushed from the main screen: history is deeper into the app, not a dialog over it. Months, not weeks: a month is the unit people judge "how am I doing" in and it gives the group header a meaningful aggregate; weekly headers would turn a long history into a picket fence of titles.
- `HistoryProps.isRunning` — picks which action the empty state offers (`HistoryEmptyAction`).
- `HistoryProps.isPro` — `unknown` locks the export exactly like `free`: Pro is never handed out on a guess.
- `HistoryProps.exportFile` — the written CSV waiting to be shared; the share sheet is up while it exists.
- `HistoryProps.isExportBusy` — mirrors `HistoryState.isExportBusy`, so the button is gated the same way the thunk gates itself.
- `HistoryFlowView.source` — logged with the open. The eating-window entry arrives with the fast that just closed already expanded: the link named it ("Last fast · 16h 24m"), so the screen should not make it be hunted for.
- `HistoryFlowView.focusRecordID` — a record to open expanded: the eating-window entry names its record in the link, the overlap refusal names one in its reason. Both arrive at a screen where hunting for it is the whole cost of the trip.
- `HistoryFlowView.body` — empty state action — both choices leave the screen; only the invitation (`.startFast`) also starts a fast on the way out.
- `HistoryFlowView.body` — `.toolbar(.hidden, for: .navigationBar)` hides the bar but the back button is *not* separately hidden: that modifier switches the pop gesture off outright. Hiding the bar suppresses the gesture too, so `InteractivePopGesture` puts it back.
- `HistoryFlowView.body` — the share sheet is Apple's, so it is presented the system way (`.sheet`) rather than as an overlay with our own motion numbers.
- `HistoryFlowView.exportButton(theme:)` — a labelled row makes the Pro gate visible before the tap. Locked, the control is a door rather than a statement, and a door naming one benefit reports its own trigger (`.historyExport`) instead of borrowing `.manual`: `manual` means "the user went looking for the offer", this means "the user asked for the export and found a padlock", and the offer opens on the export because of it. Splitting a low-volume column is fine — this is the only entry whose trigger says what the person wanted.
- `HistoryFlowView.exportButton(theme:)` — trailing slot width — the locked PRO capsule needs 76pt, the unlocked share circle 44pt; keeping the wider slot after purchase strands the icon 32pt from the card's trailing edge.
- `HistoryFlowView.exportButton(theme:)` — accessibility — the lock badge is hidden from the tree and the label overrides the glyph, so without `accessibilityValue` and `accessibilityHint` the locked and unlocked states are indistinguishable to VoiceOver. The tier goes in the value, not only the hint, because hints are switchable and delayed: a gate needs one channel the user cannot turn off. Accessibility id `history.export`.
- `HistoryFlowView.content(stats:theme:)` — `HistorySummaryCard` gets the same streak projection the main screen shows: one rule, one number.
- `HistoryFlowView.content(stats:theme:)` — `showsFirstNote` reads the raw counter, not the projection: whether the reader is a beginner is a fact about their past, and a streak that lapsed yesterday displays 0 without making them one.
- `HistoryFlowView.content(stats:theme:)` — charts, when they come, slot between the totals and the first group, so adding them shifts nothing above or below.
- `HistoryFlowView.monthGroup(_:theme:)` — on a long history the group aggregate carries the value, not the rows.
- `HistoryFlowView.toggle(_:)` — accordion: at most one record open, so the screen never becomes a wall of detail.
- `InteractivePopGesture` — puts the system edge-swipe back on a screen that hides the navigation bar. Hiding the bar takes the pop gesture with it and the recogniser is not merely disabled — the navigation controller's own delegate vetoes it in `gestureRecognizerShouldBegin`, so flipping `isEnabled` alone changes nothing; both the flag and a delegate are set. Not a `DragGesture`: a hand-rolled one does not track interactively, does not mirror to the trailing edge in RTL, and would compete with the horizontal drag `SwipeToDeleteRow` owns. Nothing is drawn — the controller exists only to reach the navigation controller — so the header is untouched and no system back button appears.
- `InteractivePopGesture.Host.borrowed` — the recogniser belongs to the navigation controller, which outlives this screen, so what was borrowed is given back in `viewWillDisappear`. A delegate left behind on the root is the classic way to wedge navigation for good.
- `InteractivePopGesture.Host.previousEnabled` — `isEnabled` is given back too, not only the delegate: a flag deliberately false elsewhere would otherwise stay on after this screen and misfire far from here.
- `InteractivePopGesture.Host.gestureRecognizerShouldBegin(_:)` — the depth check is not ceremony: allowing the gesture on the root view controller makes a navigation controller stop responding to pushes afterwards. The delegate is replaced wholesale, not proxied: the original is no longer asked any of the five methods, and the rest fall back to protocol defaults. That holds only because the one behaviour known from it — its answer on simultaneous recognition — is reproduced in `gestureRecognizer(_:shouldRecognizeSimultaneouslyWith:)`.
- `InteractivePopGesture.Host.gestureRecognizer(_:shouldRecognizeSimultaneouslyWith:)` — the rows own a horizontal drag; the two must not run together.
- `SwipeToDeleteRow` — trailing swipe reveals Delete; a full swipe never deletes on its own: the confirmation is the point, there is no undo.
- `SwipeToDeleteRow.direction` — the row travels toward the trailing edge, whichever side that is (RTL).
- `SwipeToDeleteRow.body` — the action fills exactly the strip the row was pulled aside by, so it never sits under the translucent row content at rest. Accessibility id `history.row.delete`.
- `SwipeToDeleteRow.swipeableContent` — iOS 26 lets a child SwiftUI `DragGesture` capture a vertical touch before its direction guard runs, even when simultaneous with the `ScrollView`. A UIKit pan (`HorizontalRowPan`) can fail in `gestureRecognizerShouldBegin` while the touch is still being arbitrated, so vertical motion goes straight to scrolling. iOS 17 keeps the `DragGesture` because `UIGestureRecognizerRepresentable` starts at iOS 18.
- `HorizontalRowPan` — direction-locking pan: SwiftUI receives it through the native gesture bridge, UIKit gets the early-failure hook that leaves vertical movement to the enclosing scroll view.
