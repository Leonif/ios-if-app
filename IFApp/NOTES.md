# IFApp root - notes for agents

Why the app entry point and the notification manager are the way they are. Folders below have their own `NOTES.md`; this one covers only the two files at the root of `IFApp/`. Read the section of a file before editing it; an edit that changes or cancels a point below updates the point in the same commit.

## IFAppApp.swift

- `IFAppApp.init()` — `-showStreakMilestone` — UI tests force the streak milestone card open; pair it with `-seedStreak N` so the title shows a real day count. A contract with the Maestro flows.
- `IFAppApp.configureFirebase()` — configures Firebase only when the SDK is linked and the config plist is bundled: without the plist `configure()` crashes. Internal builds point at a separate Firebase project ("IF24 Debug", `GoogleService-Info-Debug.plist`) so testing never lands in production analytics. On devices that look like mainland China Firebase is never configured (`looksLikeMainlandChina`).
- `IFAppApp.looksLikeMainlandChina` — true when any of three signals says the user is probably in mainland China: App Store storefront, device region, or preferred language. Sending events to Firebase from mainland China is a cross-border transfer of personal information (个人信息保护法, art. 38-39), which needs separate consent (单独同意) plus a CAC mechanism, and the app has neither. Not configuring Firebase at all means there is no transfer and nothing to consent to, so the gate sits on `FirebaseApp.configure()` and not on event logging: a configured SDK registers the installation and talks to Google on its own, which is already the transfer.
- `IFAppApp.looksLikeMainlandChina` — the three signals are OR'd on purpose. None proves physical presence, which is what PIPL art. 3(2) attaches to: someone in Shanghai with a US Apple ID trips none of them, a Vancouver expat with device region CN trips all three. A false positive costs a few rows of analytics, a false negative is the violation — the "redundant" conditions are the point, do not simplify them away. This is the owner's chosen variant (stay in the Chinese storefront, send nothing from it); background and the acceptance criterion are in the wiki page `privacy-label.md`, item (г).
- `IFAppApp.looksLikeMainlandChina` — storefront — StoreKit 2's `Storefront.current` is async and this answer is needed synchronously before Firebase is configured, so the StoreKit 1 property is read. `nil` (store unreachable, or not resolved yet at cold start) means this signal does not vote.
- `IFAppApp.isSimplifiedChinese(_:)` — Simplified Chinese in any spelling (`zh-Hans`, `zh-Hans-CN`, `zh-CN`, bare `zh`). Traditional Chinese is left out: Hong Kong, Taiwan and Macao are separate storefronts and PIPL does not reach them.
- `IFAppApp.tagInternalTraffic()` — stamps every event from non-App-Store builds (Xcode DEBUG, simulator, TestFlight) with `traffic_type = internal`, so GA4's built-in Internal Traffic filter excludes testing from real-user reports. App Store production builds are left untagged.
- `IFAppApp.isInternalBuild` — only a positively identified App Store build counts as production; anything else is internal. A locally built Release app also reports a receipt URL ending in "receipt" but has no file there, so the existence check separates it from a real App Store install. TestFlight carries a "sandboxReceipt" file and stays internal.

## NotificationManager.swift

- `NotificationManager.foregroundPresenter` — held here because `UNUserNotificationCenter.delegate` is weak: a presenter created at the call site would be released at once and the centre would go back to swallowing foreground deliveries silently.
- `NotificationManager.enableForegroundPresentation()` — lets local pushes show while the app is open. Without a centre delegate iOS delivers a notification whose moment arrives in the foreground to nobody, so the goal-reached and eating-window-closed pushes would never appear for someone sitting on the screen they are about. Must run before launch finishes, since a notification can be due the instant the app opens.
- `NotificationManager.requestAuthorization()` — shows the system dialog and waits for the answer. The caller must await it: reading `authorizationStatus()` before it returns records the state from before the dialog, not the user's decision. A thrown error means "not granted"; what gets recorded is the read-back of the real status, never this flag.
- `NotificationManager.authorizationStatus()` — read each time because the user may change it in Settings.
- `NotificationManager.goalReachedID` — one fixed identifier, so the goal-reached push is a single replaceable request; `scheduleGoalNotification(after:)` cancels the previous one first. Fires even if the app is backgrounded or killed.
- `NotificationManager.eatingEndID` — the same single-replaceable-request scheme for the eating-window-closed push (`scheduleEatingEndNotification(after:)`).
- `NotificationManager.cancelDailyReminders()` — removes the legacy fixed daily reminders (noon / evening) still scheduled on installs that had them.
- `ForegroundPresenter` — presents every local push the app schedules (goal reached, eating window closed, Sunnah reminders) the same way in the foreground as in the background: banner, Notification Center entry and sound. Nothing is filtered by identifier: each is scheduled for a moment the user asked to be told about, and being inside the app at that moment is not a reason to stay silent. `didReceive` is deliberately not implemented: a tap keeps the system default of opening the app.
