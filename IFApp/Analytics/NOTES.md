# Analytics - notes for agents

Why the event catalog and its transport are the way they are. Event and parameter names here are a contract with GA4 / Firebase: renaming one breaks the series and GA4 backfills nothing. Read the section of a file before editing it; an edit that changes or cancels a point below updates the point in the same commit.

## AnalyticsClient.swift

- `DefaultAnalyticsClient` — the transport: sends to Firebase when the SDK is linked, otherwise prints to the console, so analytics work in dev and test builds without Firebase.
- `DefaultAnalyticsClient.isFirebaseConfigured` — Firebase is deliberately left unconfigured on mainland-China devices and on any build without the config plist (`IFAppApp.configureFirebase()`). Every event then drops here silently; the rest of the app keeps working.
- `AnalyticsClient.setUserProperty(_:forName:)` — a persistent user property for segmentation; `nil` clears it.

## AnalyticsEvent.swift

- `AnalyticsEvent` — the product's funnel event catalog, one place to see everything tracked. Names are snake_case (Firebase convention, at most 40 characters).
- `AnalyticsEvent.parameters` — anything meant to be read as a breakdown travels as text. A GA4 custom dimension reads only the parameter's string field; a value logged as a number (or as a `Bool`, which bridges to `NSNumber`) leaves that field empty and every row comes back `(not set)`, and GA4 backfills nothing. A number stays a number only where the question is an average, i.e. where the console definition is a custom metric — `duration_seconds` alone. See `ARCHITECTURE.md`, "Типы параметров GA4".
- `code(_:width:)` — a number on its way into a GA4 dimension: text, zero-padded to a fixed width. The padding is not decoration: these dimensions are read by the shape of the distribution, i.e. sorted by the dimension, and string sort puts `9` after `16` unless the widths match. Values wider than `width` still log correctly; only their place in the sort degrades, and at that size the value is an outlier read one row at a time anyway.
- `AnalyticsEvent.appOpened` — the app launched or was foregrounded into use.
- `AnalyticsEvent.fastStarted` — `goal_hours` is the chosen plan's fasting window.
- `AnalyticsEvent.fastStopped` — `completed` means the fast had reached its goal. `stage` is the phase the fast was in as a stable code (`fed` / `sugar` / `fat` / `ketosis` / `autophagy`), never the displayed label, which differs per locale and makes the dimension impossible to group.
- `AnalyticsEvent.fastStopped` — `duration_seconds` — the only number left on purpose: not a breakdown but the raw quantity a custom metric averages.
- `AnalyticsEvent.fastStopped` — `end_backdated_minutes` — how far behind the tap the ending was placed, text padded to 4. Read as a distribution: zero is "confirmed as it stood", minutes are a correction, hours are someone who forgot to stop — the population the correction sheet exists for, which a plain `duration_hours` would count as having fasted that long.
- `AnalyticsEvent.fastStopUndone` — the user took an ending back from the result screen. No parameters: the one question it answers is whether the undo earns its place, and that is a count. For analysis: the `fast_stopped` it undoes has already fired and stays in the counters, so cancelled endings have to be subtracted or `fast_stopped` reads high.
- `AnalyticsEvent.goalReached` — the fast reached its goal (the goal-reached moment fired); `goal_hours` is the plan window.
- `AnalyticsEvent.fastReset` — `elapsed_minutes` is whole minutes from the start of the fast to the reset, and that number is the whole point of the event: minutes mean the user was fixing a wrong start time, hours mean they abandoned the fast. Read as a distribution over buckets, never as an average.
- `AnalyticsEvent.eatingWindowStarted` — the user opened the eating window from the complete screen.
- `AnalyticsEvent.fastChained` — the user started the next fast from the window-closed screen (the chain held). Accompanies `fast_started`.
- `AnalyticsEvent.timeAdjusted` — the user nudged the elapsed time (manual ± correction).
- `AnalyticsEvent.endFastRefused` — the end-fast sheet refused the chosen end because it overlaps a fast already saved. `unavoidable` means the clash is on the fast's own start, so no end could clear it — the dead-end kind. The split shows how often a real user hits a refusal and how often it is the dead end, to tell whether it needs more work. Sent as `"1"` / `"0"` text.
- `AnalyticsEvent.lastMealLogged` — the user confirmed the Last-meal picker. `backdated` = started in the past (a real meal time) vs fresh "now"; `minutes_ago` = how far back; `input_method` = which control produced the answer (`MealInputMethod`).
- `AnalyticsEvent.lastMealLogged` — `backdated` — a string, and a trustworthy one only because the meal ribbon does not seed: `MealState` holds a distance that starts at zero. A sheet that seeds its value on open reads `true` after the first open regardless, and the flag would stop saying what it claims.
- `AnalyticsEvent.lastMealLogged` — `input_method` — chip / ribbon / exact, plus untouched and seeded for the two cases that are none of the three. The point of the ribbon is that it reaches any distance, and this is the only parameter that shows whether it is actually reached for — so it is a dimension and must be text.
- `AnalyticsEvent.sourcesOpened` — the user opened the scientific Sources screen.
- `AnalyticsEvent.sourceArticleOpened` — a bundled paper opened in the reader. `article` is the paper's index in the catalog as a fixed-width code: not the title, which is localized and would give the dimension ten vocabularies, and not the URL, which would make it a list of links rather than of papers. It is also the identifier the rows are addressed by (`about.source.<id>`). Two digits, like every number that travels as a dimension: string sort keeps the papers in catalog order only while the widths match.
- `AnalyticsEvent.sourceOriginalOpened` — the user left the reader for the paper itself. Same `article` code, so the funnel (list opened, article opened, original followed) counts end to end and per paper rather than in three unrelated totals. Raised on the reader's own button only: the external-link thunk behind it also opens the privacy policy and the system settings, and an event on the thunk would count those as papers.
- `AnalyticsEvent.sourceArticleClosed` — `reached_end` means the foot of the article had been on screen at least once: the cheapest honest split between read and merely opened. An article shorter than the screen counts as reached, because its end was seen. Text, not `Bool` — see `parameters`.
- `AnalyticsEvent.sunnahOpened` — `source` is which door (`SunnahEntrySource` raw values). The question is how many people ever find the release's free headline feature, which needs the doors counted apart.
- `AnalyticsEvent.sunnahEnabled` — the user armed the Sunnah reminders. `mode` = which schedule ("weekly" / "white_days" / "both"); `push_allowed` = the notification permission was in place when the schedule was written. The second parameter is not a diagnostic: it measures the cohort who turned the feature on and will never hear from it, a product fact about the permission ask. Raised once per arming, on the permission answer rather than on the tap, because the permission is only known after it has been read. `push_allowed` is text, not `Bool`.
- `AnalyticsEvent.historyOpened` — `source` is the entry point, the raw values of `HistoryEntrySource` (four of them, `end_fast_overlap` included).
- `AnalyticsEvent.historyRecordDeleted` — the user deleted a record from the history (swipe + confirm).
- `AnalyticsEvent.historyExported` — the history was handed to the share sheet as a CSV. No parameters, deliberately: a parameter needs a custom definition registered in GA4 before submit, and none would change the one decision this event informs — whether an import is ever worth building. A cancelled share does not fire it.
- `AnalyticsEvent.historyLoadFailed` — a read of the history file did not produce today's records; `reason` is a `HistoryLoadFailure` raw value. Fires once per failed read, not once per launch: a file that cannot be moved aside reports again on every write attempt, and that repetition is the signal. Expected to stay silent forever; it exists to find out whether the corrupt-history guard in `FastHistoryRepository` ever catches anything before a release changes `FastRecord`'s shape.
- `AnalyticsEvent.reviewPrompted` — the native `requestReview` went out; `trigger` is a `ReviewPromptTrigger` raw value. Apple may or may not show the panel, but the call itself happened on an active scene, so this counts attempts really made, not attempts intended.
- `AnalyticsEvent.streakMilestone` — a streak milestone card was shown; `days` is the threshold (3/7/14/30).
- `AnalyticsEvent.planSelected` — the user picked a plan in the plan editor. `plan` is the ratio label ("16:8"), `goal_hours` that plan's fasting window. Pairs with the `current_plan` user property, which carries the same value persistently.
- `AnalyticsEvent.planConfirmed` — the plan editor was closed with whatever plan the user settled on, fired even when nothing was touched, so the plan mix counts off this one. It does not contrast with `plan_selected` as "tried on" against "kept": the wheel turns a draft inside the sheet and writes nothing, so a length spun to and abandoned produces neither event, and both fire only on a plan that got through the gate. Series from before 1.5.1 also counted the wheel's passing values.
- `AnalyticsEvent.paywallShown` — the offer screen was shown; `trigger` is a `PaywallTrigger` raw value. At 20-35 shows a month it is read as a distribution over triggers, never as a rate.
- `AnalyticsEvent.paywallDismissed` — the offer screen was closed without a purchase.
- `AnalyticsEvent.purchaseStarted` — the Buy button was tapped and Apple's sheet was asked for.
- `AnalyticsEvent.purchaseFailed` — the attempt ended without Pro; `reason` is a `PurchaseFailure` raw value. "pending" is Ask to Buy, which may still be approved later.
- `AnalyticsEvent.restoreCompleted` — Restore purchases brought the entitlement back.
- `AnalyticsEvent.themeActive` — the appearance the app is used in (`dark` = system dark mode). Fires on screen appear and on live theme switches, so count users per `theme` value to see which appearance the audience actually uses.
